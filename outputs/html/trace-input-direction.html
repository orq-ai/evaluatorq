How shared trace input works in evaluatorq

TL;DR — TraceInput is the async retrieval request, and fetch_traces() returns canonical Trace objects. An exact span is parsed alone; a trace or query selection starts at the latest eligible non-evaluator span and follows parents until messages are found. General evaluation scores recorded output, simulation converts traces into datapoints, and red teaming seeds a new dynamic attack with either first_user or last_assistant context.

One canonical record, three projections

The shared layer knows trace storage and wire formats. The surface layers know what a trace means for their workflow. This dependency direction keeps the importer deep and the public interfaces small.

The import path, step by step

Expand each step for the exact responsibility and its current code seam. The line references point to the implemented working tree.

1 · Retrieve traces and spans common/trace_input.py:619

TraceInput describes one exact trace/span pair, one trace ID, or a bounded search. fetch_traces() pages through POST /v2/traces/v3oql when needed, fetches V3 spans with bounded concurrency, and returns list[Trace]. A broken or missing span remains represented with import_error; it is not silently dropped.

from evaluatorq import TraceInput, fetch_traces

trace = (await fetch_traces(
    TraceInput(trace_id="trace_123", span_id="span_456")
))[0]
2 · Select the recorded exchange common/trace_input.py:484

The importer marks evaluator spans and every descendant as ineligible. An exact span_id means exactly that span: it is parsed once and an empty span fails explicitly. With only a trace ID or a query result, the importer chooses the latest remaining span and walks up its parent chain until it finds messages.

3 · Normalize all supported message shapes common/trace_input.py:335

Chat Completions messages, Responses input/output items, and OpenTelemetry GenAI messages are normalized to evaluatorq's shared Message contract. Candidates may live in top-level span input/output, flat or nested span attributes, or span event attributes. Tool calls and tool results survive normalization; reasoning parts are deliberately excluded.

4 · Project into a surface types.py:264 · simulation/traces.py:522

The canonical record does not guess the caller's intent. Trace.to_datapoint() creates a generic DataPoint. Simulation's async helper performs model-driven persona/scenario work. Red team's async helper selects a replay point, then red_team() combines that seed with its normal vulnerability, strategy, attack-technique, and delivery-method configuration before running a new attack.

Decisions

The design is implemented: loaded traces share one canonical model, while each surface assigns the trace the meaning appropriate to its workflow.

Settled

1. Reuse red_team()

Trace support is a data adapter, not a new action. redteam.datapoints_from_traces() creates seed rows; red_team(target=..., datapoints=...) executes the existing strategy, attack, scoring, and reporting path.

Validation: a target is always required. The recorded answer is context, not the result of the new attack.

Settled

2. Attack configuration

Vulnerabilities, categories, named strategies, attack techniques, and delivery methods stay on red_team(). Categories and strategies select the strategy set; the attacker prompt names the selected vulnerabilities, attack techniques, and delivery methods.

Same default: omitting vulnerability and category filters keeps the existing full registered sweep.

Settled

3. Replay point

first_user sends the recorded opening to a fresh target and attacks after its new reply. last_assistant imports the transcript through its final assistant turn and attacks from there.

Default: first_user works with both stateful and stateless targets. last_assistant requires a target that accepts caller-owned history.

Settled

4. Fresh isolated target

Every trace-strategy row gets a fresh target. Production thread, task, and memory identifiers are provenance only and are never reused.

Why: a security test must not alter the real conversation it learned from.

Gotchas worth knowing

  • An exact span really is exact. TraceInput(trace_id=..., span_id=...) parses only that span and reports an error if it has no messages. Only trace-only and query modes walk toward the root.
  • Evaluator descendants must be excluded together. Ignoring only the evaluator parent can still select its nested model-call span and accidentally evaluate the judge instead of the application.
  • last_assistant is not universally replayable. A hosted target that owns an opaque server-side thread cannot be made to remember an imported assistant reply. Evaluatorq rejects that combination instead of pretending the history was applied.
  • The bootstrap is context. It is visible separately in provenance and usage, is billed and included once in aggregate totals, but it does not spend an attack turn or become the response judged for vulnerability.

FAQ

Is this replacing RES-1082?
No. RES-1082 delivered trace-derived agent simulation. This direction moves its trace retrieval and normalization into a shared layer, keeps the simulation API, and lets both general evaluation and red_team() consume adapters over the same canonical trace record.
Does red teaming score the answer already stored in the trace?
No. Core evaluatorq can score the recorded answer with inference=False. Red teaming requires a target and generates a new attack after establishing the selected trace context.
Why not pass TraceInput directly to red_team()?
The async converter owns retrieval and replay-point selection while the already-large runner keeps vulnerability, strategy, attack-technique, delivery-method, validation, and reporting semantics in one place. Passing already-loaded Trace objects avoids a second fetch.
Can last_assistant continue a hosted Orq agent trace?
Yes. The current agent:<key> execution path uses the stateless Responses adapter and accepts the full caller-owned transcript. A custom or legacy adapter that owns an opaque server-side thread cannot import that assistant history; use first_user for such a target.
Where do the three formats become identical?
At the Trace boundary. Below it, the importer knows Chat Completions, Responses, and OpenTelemetry GenAI. Above it, every consumer sees evaluatorq Message objects and provenance describing the original format.
Can we add another trace backend later?
Yes. TraceInput is currently Orq-specific in retrieval behavior, while Trace is backend-neutral. A future source can produce the same canonical objects without changing the three surface adapters.
What is already decided?
Use a canonical trace record, accept one trace and optional exact span or a query, keep exact spans exact, walk only for trace/query selection, support all three message formats and locations, keep both surface converters async, score recorded output only in core evaluation, and seed new isolated red-team attacks from either the first user or last assistant turn.
