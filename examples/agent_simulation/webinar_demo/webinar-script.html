Q3 · "The user-simulator got impatient with the agent just now. Who decided it should be impatient?"
Lands during the live run when a persona's style shows in the transcript. Beat: personality comes from the generated persona — emotional arc is scripted, the conversation is not. This separates simulation from "replaying canned prompts".
Cue · Act 1 step 3, mid-simulation, react to a real transcript moment
Q4 · "Is this open source? Because most people watching don't run their agents on orq."
Ask it bluntly — it's the audience's biggest silent objection. Beats:
  • Yes — evaluatorq is open source (github.com/orq-ai/evaluatorq), pip-installable, runs anywhere.
  • The simulation engine has no platform dependency: --openai-model for any OpenAI-compatible endpoint (vLLM, OpenRouter, local), --vercel-url for any HTTP agent.
  • SDK: wrap any async fn(messages) → str. Adapters shipped for LangGraph, CrewAI, OpenAI Agents SDK, Pydantic AI.
Cue · opens Act 2 (~20:00) — this question IS the act transition
Q5 · "So minimum viable start: I have a LangGraph agent on my laptop. What are my first three commands?"
Forces concreteness. Bauke's answer: ① pip install evaluatorq ② export your LLM key ③ evaluatorq sim run --agent-description "..." or ten lines of SDK (simulate(target=...)). Under five minutes to first transcript.
Cue · end of Act 2, before Act 3
Q6 · "The dashboard's open. Teach me to read it — what do I look at first, and what do I ignore?"
The results-walkthrough driver — one question, four screens. Arian re-asks a sub-question at each screen as Bauke navigates:
  • Summary strip (goal completion, avg score, conversations, turns, errors, tokens) — "so 67% goal completion: good or bad?" Beat: it's a health check, not a diagnosis. The number says that something broke, never what.
  • Persona × scenario heatmap — "where do I look next?" Beat: failures cluster. It's rarely "the agent is bad" — it's this persona type on this scenario type. That's already an actionable hypothesis.
  • Top failure modes & rules broken — "does it tell me why?" Beat: recurring patterns ranked across conversations; pick the biggest one to fix first.
  • Transcript drill-down — "show me one." Beat: per-turn judge scores with reasoning; find the exact turn where it derails — usually a mid-conversation pivot, not turn one. Every failure is a bug report with the reproduction attached.
Cue · Act 4a (32:00), drives the inspect segment — dashboard on screen, no slide
Q7 · "OK, we found the failure. Don't tell me the workflow — show me. What do we actually do right now?"
The pivot question — it launches Act 4b instead of getting a spoken answer. Bauke hands the run to Claude Code: read .evaluatorq/sim-runs/, summarize which criteria failed for which personas, quote the derailing turns, propose the minimal instruction fix, apply it live with orq agents update boh_creditcard_agent_demo --instructions "...". While it works, Bauke narrates the frame: fix → re-run frozen set → like-for-like compare → regression gate in CI. Suite is shareable too (sim upload-dataset / --dataset-id).
Cue · pivot into Act 4b (~35:00)
Q8 · "So that's Claude Code driving the whole loop. Where's the human in this?"
Ask while the fix applies or right after make rerun shows the pass rate move. Beats:
  • It works because evaluatorq is CLI-first with machine-readable output — exactly what coding agents want.
  • The loop we just watched: read failures → patch instructions → re-run frozen set → compare. Agent iterates, human reviews the diff.
  • Honest note: the human stays on the diff. You're reviewing changes, not writing test cases.
Cue · Act 4b/4c (~37:00), while the rerun streams
Q9 · "That's basically a self-improving agent. Is that safe? What goes wrong?"
The expert-credibility card — invite Bauke to caveat:
  • The frozen suite works as a fitness function for automated iteration — that part is real.
  • The trap is Goodhart: optimize hard against one judge and you overfit to the judge, not the user.
  • Mitigations: hold out scenarios the loop never sees; extend the suite as the agent improves; periodically eyeball transcripts yourself.
Closing beat: simulation doesn't replace production data — it's how you start before you have any, and the suite keeps growing after.
Cue · interview block closer (~41:00), hand off to audience Q&A
H1 · "An LLM writing tests for an LLM — isn't that circular? Won't the generator share the agent's blind spots?"
Beats: different models, different roles — the generator isn't asked "what would this agent get wrong", it systematically explores persona × goal × adversarial-strategy combinations, which is wider than any dev's hand-written list. But concede the core: yes, generated coverage has its own distribution. That's why you extend the suite with production traces once you have them — simulation is the bootstrap, not the endpoint (same line as both LinkedIn posts).
Cue · right after the Act 1 payoff (Q2), while the generated row is on screen
H2 · "How good is the judge? Did you validate it — TPR/TNR against human labels?"
The question this audience will definitely ask. Honest beats:
  • Judges are prompt-based (goal_achieved, criteria_met) and every verdict ships with per-turn reasoning — you audit them, not trust them.
  • Criteria are explicit and per-scenario, so the judge grades against a written contract, not vibes.
  • No shipped TPR/TNR benchmark — say so. Recommended practice: spot-check verdicts on your first runs, tune criteria wording where the judge and you disagree. Same discipline as any LLM-as-judge.
Cue · Act 4a, judge reasoning visible in the transcript drill-down
H3 · "The conversations are stochastic — same frozen datapoints, different dialogue every run. How is that a regression gate?"
Sharpest technical objection. Beats:
  • Freezing datapoints removes the biggest variance source — the test inputs. What varies is the path, not the goal.
  • Criteria are outcome-level ("balance disclosed only after verification"), not path-level — robust to different phrasings of the same conversation.
  • Gate on pass-rate deltas, not single binaries; re-run flaky rows like you re-run flaky tests. It's a statistical gate, same as any nondeterministic system test.
Cue · Act 3a, the moment the frozen re-run is proposed
H4 · "How many personas × scenarios is enough? Is there a coverage measure?"
Honest beats: no formal coverage metric — heuristic is saturation. Start 3 × 3, extend (Act 3b) until new scenarios stop surfacing new failure modes. The persona × scenario heatmap doubles as the coverage map: uniform green with sparse cells means generate more, clustered red means fix before growing.
Cue · Act 3b, while the extend command runs
H5 · "Hundreds of multi-turn conversations, three LLM roles — what does a run actually cost?"
Beats: the dashboard shows tokens total and per conversation — point at it, don't hand-wave. Cost knobs: personas × scenarios count, max turns, and model choice per role — the user-simulator and judge can run on cheaper models than the agent under test. A 3 × 3 × ~10-turn run is lunch money; the point is you spend it before users find the failure, not after.
Cue · Act 4a, tokens panel on screen — or audience Q&A

Demo cue sheet — exact commands

Mirrors RUNBOOK.md in the repo (examples/agent_simulation/webinar_demo). Agent is boh_creditcard_agent_demo — recreate any time with make provision.

Act 1 — from scratch (08:00)
# 1. generate from the agent's own description
uv run evaluatorq sim generate \
  --target agent:boh_creditcard_agent_demo \
  --num-personas 3 --num-scenarios 3 \
  -o boh_datapoints.jsonl

# 2. the payoff — read one generated row aloud
uv run evaluatorq sim validate-dataset boh_datapoints.jsonl

# 3. run live, freeze the set for Act 3
uv run evaluatorq sim run \
  --target agent:boh_creditcard_agent_demo \
  --save-datapoints boh_datapoints.jsonl \
  --name boh-from-scratch

# 4. pass rate + a failing transcript
uv run evaluatorq sim runs
uv run evaluatorq sim ui .evaluatorq/sim-runs/<run>.json
Act 2 — non-orq agents (20:00)
# CLI: any OpenAI-compatible endpoint
uv run evaluatorq sim run --openai-model gpt-4o-mini \
  --agent-description "Support agent for ..." \
  --name boh-nonorq-cli

# CLI: any deployed HTTP agent
uv run evaluatorq sim run \
  --vercel-url https://my-agent.vercel.app/api/chat \
  --agent-description "..."

# SDK: wrap anything that answers a message
from evaluatorq.simulation import simulate

async def my_agent(messages) -> str: ...

results = await simulate(
    target=my_agent,
    evaluator_names=["goal_achieved",
                     "criteria_met"])
Act 3 — working with data (27:00)
# 3a. re-run the EXACT same set after a prompt tweak
uv run evaluatorq sim simulate \
  --target agent:boh_creditcard_agent_demo \
  --datapoints boh_datapoints.jsonl \
  --name boh-rerun

# 3b. extend the suite — generate more, append
uv run evaluatorq sim generate \
  --target agent:boh_creditcard_agent_demo \
  --num-personas 2 --num-scenarios 2 -o more.jsonl
cat more.jsonl >> boh_datapoints.jsonl
uv run evaluatorq sim validate-dataset boh_datapoints.jsonl

# 3c. push to an orq dataset + re-run from the platform
uv run evaluatorq sim upload-dataset \
  -i boh_datapoints.jsonl -n "Bank of Holland Sim Set"
uv run evaluatorq sim simulate \
  --target agent:boh_creditcard_agent_demo \
  --dataset-id <id>
Act 4 — inspect, harden, re-run (32:00)

If it breaks — contingencies & honest answers

First three are demo failures with a rehearsed fallback. Last three are audience questions that deserve an honest "not yet" — saying it confidently is part of the "this is new and moving fast" story.

Situation
Sev
Response
Live Bank of Holland agent unreachable mid-demo (platform hiccup, key expired; make provision recreates it, but not on-stream).
HIGH
Switch to --agent-description "..." — no platform call needed for generation; for the run, fall back to the --openai-model stand-in agent rehearsed in the dry run. Narrate the switch: "this also shows it works without orq."
Generation or simulation runs slow on the stream — dead air.
HIGH
Arian fires Q1/Q2/Q3 to fill (that's what the cues are timed for). If >2 min, open backup_datapoints.jsonl / the pre-baked run JSON in sim ui and keep the live one running in a second tab.
Dashboard (make dashboard / sim ui) fails to open or renders wrong on the shared screen.
MED
Two viewers = mutual fallback (FastHTML on :8000, Streamlit via sim ui). Last resort: sim runs table + read the failing transcript from the run JSON. Less pretty, same story.
Claude Code goes sideways during the live fix (Act 4b) — wrong diagnosis, over-broad edit, or just slow.
HIGH
Keep the dry run's known-good instruction fix in a scratch file; apply it manually with orq agents update boh_creditcard_agent_demo --instructions "..." and continue to make rerun. Narrate honestly: "the agent proposed something broader than I want on stage." Note: use orq, not orqi — orqi agent update 404s (RUNBOOK Gaps §6).
"Can I push the suite to an orq dataset and run from there?"
LOW
Yes — new this week: sim upload-dataset -i suite.jsonl -n "...", then sim simulate --dataset-id <id> (Act 3c shows it live). Honest caveat: the dataset API only takes scalar inputs, so persona/scenario display as JSON strings in the orq UI, not structured fields.
"Why is there no orq sim command?"
LOW
Deliberate split: orq CLI = platform CRUD (agents, datasets, evals); evaluatorq = the open-source evaluation engine. Simulation lives with the engine.
"Can it seed from my existing data AND generate more in one go?"
LOW
Not natively yet — dataset_id is still mutually exclusive with personas/scenarios. Today: generate separately, then append locally (Act 3b) or upload-dataset --dataset-id to extend the platform copy. No LLM augmentation from existing rows yet. Say so plainly.
"How does this compare to τ-bench, DeepEval's conversation simulator, LangSmith simulations?"
MED
Don't trash anyone — same family (persona-driven user simulation), credit the idea. Differentiators to name: suite generated from just an agent description, frozen JSONL is portable and diffable, targets are framework-agnostic (orq / OpenAI-compatible / HTTP / any Python callable), open source end to end. τ-bench is a fixed benchmark; this builds your benchmark.
