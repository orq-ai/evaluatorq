The gap — you already run evals

Majority of evaluation datasets are single-turn,
production failures usually happen after many turns

  • Golden sets + LLM-as-judge test responses, not conversations
    Agents break when users change their mind, get impatient, contradict themselves, or drift off-goal — conversational dynamics no static golden set encodes.
    turn 7, not turn 1
  • And at the start, there's no dataset at all
    The agent hasn't shipped — no production traces to mine, and multi-turn ground truth is the most expensive kind to hand-build.
    cold start
  • You can't write test cases for failure modes you haven't met
    The blind spots are exactly the point — coverage has to come from somewhere other than your own imagination.
    unknown unknowns
The idea

From nothing to a test suite

One input, one pass, two outputs: judge scores you can read, and a reusable dataset for your evaluation pipeline.

Under the hood

The system, and where you can extend

1 Target — anything that answers a message: AgentTarget protocol; adapters for LangGraph, CrewAI, OpenAI Agents SDK, Pydantic AI.  2 Judge — choose evaluators per run (evaluator_names=[...]) or write your own.  3 Data — skip generation: bring --datapoints JSONL or --dataset-id; extend and upload back.  4 Outputs — run store feeds the dashboard, CI gates, and orq experiments.

Live demo

Let's break an agent.

A live credit-card support agent, zero test data. From here it's all terminal.

Everything you're about to see is open source — evaluatorq, pip-installable.
Demo · Act 1

Three commands, one suite

# 1 — generate personas × scenarios from the agent's description
evaluatorq sim generate --target agent:boh_creditcard_agent_demo \
  --num-personas 3 --num-scenarios 3 -o datapoints.jsonl

# 2 — run the simulation against the live agent, freeze the set
evaluatorq sim run --target agent:boh_creditcard_agent_demo \
  --save-datapoints datapoints.jsonl --name from-scratch

# 3 — open the run viewer: pass rate + transcripts
evaluatorq sim ui .evaluatorq/sim-runs/<run>.json

The payoff moment: open the JSONL and read one row — a persona with patience, assertiveness, and an emotional arc, crossed with a scenario that has a goal and explicit pass/fail criteria. Coverage from nothing.

Demo · Act 2

Not an orq agent? Still works.

# any OpenAI-compatible model or endpoint
evaluatorq sim run --openai-model gpt-4o-mini \
  --agent-description "Support agent for ..."

# any deployed HTTP agent
evaluatorq sim run --vercel-url https://my-agent.app/api/chat
# or the SDK — wrap any async fn(messages) -> str
from evaluatorq.simulation import simulate

results = await simulate(target=my_agent,
    evaluator_names=["goal_achieved", "criteria_met"])

Framework adapters included: LangGraph, CrewAI, OpenAI Agents SDK, Pydantic AI — anything that can answer a message can be simulated.

Demo · Act 3

Three ways to work with data

  • ① From scratch
    No data at all — generate the suite from the agent description. What we did in Act 1.
    sim generate
  • ② Re-run frozen
    Change the agent's prompt, re-run the exact same datapoints — from a local JSONL or an orq dataset. Like-for-like comparison; regressions become a gate, not a surprise.
    --datapoints · --dataset-id
  • ③ Extend & share
    Generate more personas and scenarios, append — or push the suite to an orq dataset for the whole team (sim upload-dataset).
    generate → append → upload
Beyond the demo

What you do with it

  • Regression gate. Frozen suite re-runs on every prompt or model change — in CI, before merge.
  • Drive it from Claude Code — you just watched it. CLI-first with JSON output: the agent read the failures, patched the instructions, re-ran the frozen set. You review the diff.
  • Self-improving workflows — with one caution. The frozen suite is a fitness function for automated iteration. Keep held-out scenarios so you optimize the agent, not the judge.
